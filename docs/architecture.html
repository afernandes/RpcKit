Arquitetura

Camadas, componentes, fluxo de uma chamada simples e fluxo de uma sessão duplex roteada para um agente remoto.

Camadas

Quatro projetos no src/, com fronteira clara entre transport-neutral (em baixo) e SignalR-specific (em cima).

ProjetoTipos principaisDependências
Rpc.Contracts [RpcContract], [RpcMethod], IDuplexCall<TUp, TDown> nenhuma
Rpc.Core RpcAddress, Capability, IRpcInvoker, IRpcClient, RpcClient, ProxyRegistry, DispatcherRegistry, DuplexCallChannel, DeferredDuplexCall, JsonDuplexAdapter, RpcException Rpc.Contracts
Rpc.SignalR.Server RpcHub, IRpcRouter / RpcRouter, DeviceRegistry, PendingDuplexRegistry, InProcessRpcInvoker, extensões DI Rpc.Core + Microsoft.AspNetCore.App
Rpc.SignalR.Client SignalRRpcInvoker, RpcConnectionHost, RpcClientBuilder, RpcClientOptions, handlers do agente Rpc.Core + Microsoft.AspNetCore.SignalR.Client

Por que essa fronteira importa: os contratos e a abstração de cliente (IRpcClient.For<T>) não sabem nada sobre SignalR. Trocar o transporte (LAN isolada via mDNS, named pipes, gRPC) muda só a camada de cima. Os proxies/dispatchers e a UI Blazor não sofrem refactor.

Componentes do servidor

  • RpcHub — único SignalR Hub. Métodos: Invoke, OpenStream, OpenDuplex, mais os retornos da correlation (SubmitDuplexResponse, CompleteDuplexResponse, FailDuplexResponse). Faz handshake no OnConnectedAsync e cleanup no OnDisconnectedAsync.
  • IRpcRouter / RpcRouter — toda a lógica de roteamento mora aqui. O Hub é fino, delega ao router. Isso permite que o InProcessRpcInvoker (usado pelo Blazor Server local) também use o mesmo router sem precisar de loopback SignalR.
  • DeviceRegistry — mapa em memória DeviceId → (ConnectionId, TenantId, UserId, Capabilities[]). Suporta resolução por device id, por capability+tenant, e por user+capability.
  • PendingDuplexRegistry — sessões duplex em voo, indexadas por correlationId e por ConnectionId do agente (para cancelar tudo quando ele desconecta).
  • DispatcherRegistry (do Core) — handlers locais do servidor (ex: IOrderService implementado no próprio API).

Componentes do cliente

  • RpcConnectionHost — IHostedService. Constrói o HubConnection com WithAutomaticReconnect, monta a query string do handshake (deviceId, capabilities, tenantId, userId, opcionalmente JWT) e conecta.
  • SignalRRpcInvoker — implementação de IRpcInvoker. Traduz InvokeAsync / OpenStreamAsync / OpenDuplexAsync em chamadas SignalR (InvokeAsync, StreamAsync, StreamAsync com ChannelReader upstream).
  • AgentDuplexSessions — quando o cliente também é agente, registra os callbacks HandleInvoke, ServeDuplex, DuplexUpstream, DuplexComplete, DuplexCancel. Mantém o mapa de sessões correlacionadas localmente.
  • RpcClientBuilder — fluent API pra registrar proxies e handlers durante AddRpcClient(...).

Fluxo de uma chamada simples (Invoke)

O InvokeAsync<T> servidor→cliente (azul) é primitiva do SignalR moderno (>= .NET 7), o que permite request/response síncrono em direção contrária ao normal. Sem essa primitiva, precisaríamos do mesmo padrão de correlation que usamos pro duplex.

Fluxo de um duplex remoto

O caso difícil. SignalR não tem primitiva nativa para o servidor invocar um método streaming num cliente específico. Quando o caller pede um duplex e o alvo é um agente remoto, o router usa correlation IDs e quatro mensagens auxiliares (ServeDuplex, DuplexUpstream, DuplexComplete, DuplexCancel) para amarrar dois streams half-duplex em um duplex lógico.

Azul: caller → Hub. Verde: Hub → caller (server-streaming nativo). Amarelo: Hub → agente (SendAsync com correlation, fora do protocolo de streaming).

O protocolo em prosa:

  1. Caller abre um stream duplex SignalR pro Hub passando InvokeEnvelope + sua ponta de upstream (TUp como JSON).
  2. Router resolve o ConnectionId do agente alvo, gera um correlationId, registra uma PendingDuplexSession e envia ServeDuplex para o agente.
  3. Agente recebe ServeDuplex, acha o dispatcher local, cria canais internos e roda o dispatcher.
  4. Cada vez que a impl do agente emite um TefEvent, o agente chama connection.InvokeAsync("SubmitDuplexResponse", corr, json). O Hub repassa via session.Downstream.Writer, que é o stream IAsyncEnumerable<string> sendo enumerado pelo caller.
  5. Cada vez que o caller faz call.SendAsync(TefResponse), isso entra no upstream do stream. O Router lê e repassa via SendAsync("DuplexUpstream", corr, json).
  6. Quando a impl termina (sucesso ou erro), o agente envia CompleteDuplexResponse (ou FailDuplexResponse), o Hub fecha o downstream e o caller sai do await foreach.
  7. Se o caller cancela ou disposa, o Router envia DuplexCancel ao agente, que pára o dispatcher via CancellationTokenSource.Cancel() — o loop CliSiTef interrompe na próxima leitura de upstream.
  8. Se o agente desconecta, OnDisconnectedAsync cancela todas as sessões com aquele ConnectionId. O caller recebe OperationCanceledException imediatamente.

Blazor Server: caminho in-process

O Sample.Server.Api também usa IRpcClient para invocar handlers (servidor ou remotos). Mas o Blazor Server roda no servidor — abrir um HubConnection para o próprio /rpc seria um loopback caro.

Solução: InProcessRpcInvoker. Implementa IRpcInvoker em cima diretamente do IRpcRouter, pulando o stack SignalR para chamadas locais e mesmo para chamadas remotas (o router já faz a parte do Clients.Client(...)). Registrado automaticamente por AddRpcServer(). 

// no Program.cs do Sample.Server.Api
builder.Services.AddRpcServer();           // registra IRpcInvoker = InProcessRpcInvoker

// na página Blazor — mesma API que o MAUI usaria
var orders = await Rpc.For<IOrderService>(RpcAddress.Server)
                      .GetOpenOrdersAsync(ct);
