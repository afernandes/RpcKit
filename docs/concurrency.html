Concorrência

Flag Exclusive = true nos contratos

Quando o recurso fisicamente só permite uma operação por vez — pinpad, gaveta de dinheiro, leitor biométrico — marque o método como Exclusive. O router rejeita a 2ª chamada com RpcException(Kind = "Busy") antes de chegar no agente, economizando uma viagem de rede e dando feedback imediato ao caller. 

[RpcContract]
public interface ITefService
{
    [RpcMethod(1, Exclusive = true)]
    IDuplexCall<TefResponse, TefEvent> Charge(TefRequest initial, CancellationToken ct);
}

O lock é por tupla (ConnectionId, ContractId, MethodId). Implicações:

  • Dois agentes diferentes podem executar Charge ao mesmo tempo — são pinpads distintos.
  • O mesmo agente não pode receber duas Charge simultâneas — é o mesmo pinpad.
  • Quando o agente desconecta, todos os locks daquele ConnectionId são liberados (ExclusiveCallRegistry.ReleaseAllForConnection).
  • Ao dispor o duplex em voo, o lock libera automaticamente.
Não marque Exclusive em métodos que aceitam concorrência (impressão, consultas, atualizações de estoque). Forçar serialização global onde não precisa mata throughput sem ganhar nada.

Defesa em profundidade no handler

Mesmo com Exclusive = true, vale ter um SemaphoreSlim dentro do impl. Razões:

  • Outro processo no mesmo host pode abrir o driver USB direto (ex: app MAUI nativo) — o router não vê.
  • Reinicialização do servidor zera os locks; uma chamada antiga ainda em voo no agente continuaria.
  • Documenta a intenção no código do handler.
public sealed class TefServiceImpl : ITefService
{
    private readonly SemaphoreSlim _pinpadLock = new(initialCount: 1, maxCount: 1);

    public IDuplexCall<TefResponse, TefEvent> Charge(TefRequest initial, CancellationToken ct)
    {
        if (!_pinpadLock.Wait(0))
            throw new RpcBusyException("Outra transação TEF está em andamento neste pinpad.");

        var call = new DuplexCallChannel<TefResponse, TefEvent>(ct);
        _ = Task.Run(async () =>
        {
            try { await RunCliSiTefLoopAsync(initial, call); }
            finally { _pinpadLock.Release(); }
        }, call.Token);
        return call;
    }
}

Fila de impressão com Channel<T>

Impressão é por natureza sequencial num driver físico, mas não exclusiva — callers concorrentes não precisam ser rejeitados, devem entrar na fila. O agente mantém um Channel<T> com backpressure (rejeita se a fila encher) e um worker que processa em FIFO. 

public sealed class PrinterServiceImpl : IPrinterService, IHostedService
{
    private readonly Channel<QueuedJob> _queue = Channel.CreateBounded<QueuedJob>(
        new BoundedChannelOptions(capacity: 32) { FullMode = BoundedChannelFullMode.Wait });

    public Task StartAsync(CancellationToken _) { Task.Run(ProcessQueueAsync); return Task.CompletedTask; }

    public async Task<PrintResult> PrintAsync(PrintJob job, CancellationToken ct)
    {
        var tcs = new TaskCompletionSource<PrintResult>(TaskCreationOptions.RunContinuationsAsynchronously);
        await _queue.Writer.WriteAsync(new(job, tcs, ct), ct);
        return await tcs.Task;     // caller espera o SEU job sair, não bloqueia outros
    }

    private async Task ProcessQueueAsync()
    {
        await foreach (var (job, tcs, ct) in _queue.Reader.ReadAllAsync())
        {
            try { tcs.TrySetResult(await DoPrintAsync(job, ct)); }
            catch (Exception ex) { tcs.TrySetException(ex); }
        }
    }
}

Características desta abordagem:

  • Backpressure por canal bounded — quando a fila enche (32 jobs), o 33° caller espera o canal abrir. Evita memória crescer descontroladamente.
  • Caller espera seu próprio job — recebe PrintResult quando a impressora terminou, não quando entrou na fila.
  • Cancelamento individual — se o caller cancela enquanto o job está enfileirado, descarta sem imprimir.
  • FIFO global — não há prioridade. Se precisar, adicione uma fila por capability.

Gateway de aplicação esconde o transporte

A UI não deve depender de ITefService + IRpcClient. Em MAUI rodando no mesmo host do pinpad, o RPC é desperdício — chama CliSiTef direto. Em Blazor Server, precisa do RPC. O padrão certo é ports & adapters: 

// no domínio:
public interface ITefGateway
{
    IDuplexCall<TefResponse, TefEvent> Charge(TefRequest req, CancellationToken ct);
}

// em MAUI Windows / Self-Checkout:
public sealed class DirectTefGateway(ICliSiTefBindings sitef) : ITefGateway
{
    public IDuplexCall<TefResponse, TefEvent> Charge(TefRequest req, CancellationToken ct) =>
        /* usa CliSiTef direto, sem RPC */;
}

// em Blazor Server / ASP.NET:
public sealed class RemoteTefGateway(IRpcClient rpc, ICurrentUser user) : ITefGateway
{
    public IDuplexCall<TefResponse, TefEvent> Charge(TefRequest req, CancellationToken ct) =>
        rpc.For<ITefService>(RpcAddress.User(user.UserId, Capability.Tef)).Charge(req, ct);
}

DI escolhe a implementação por host:

// MAUI Hybrid Blazor:
services.AddSingleton<ITefGateway, DirectTefGateway>();

// API ASP.NET hospedando Blazor Server:
services.AddScoped<ITefGateway, RemoteTefGateway>();

A página Razor injeta ITefGateway e não sabe qual transporte está rodando atrás. Veja Novos contratos para o passo-a-passo.

UX do caller após Busy

O caller decide o que fazer. Padrões comuns:

  • TEF: mostrar mensagem "Outra transação em andamento. Aguarde." e desabilitar o botão. Não retry automático — pinpad tem timeout do adquirente, retry tarde fede.
  • Comando de admin (cancelar última transação): retry com backoff curto (~500ms) algumas vezes; falha definitiva se persistir.
  • Sync periódico: ignorar o erro; o próximo ciclo tenta de novo.

O que o teste de integração cobre

Exclusive_duplex_rejects_second_concurrent_call_with_Busy_without_hitting_agent verifica três invariantes:

  1. 1ª chamada abre o duplex no agente (impl invocada).
  2. 2ª chamada concorrente recebe RpcBusyException sem que o agente seja invocado uma segunda vez.
  3. Após dispor a 1ª, o lock libera e a 3ª chamada vai adiante normalmente.
