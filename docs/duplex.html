Duplex e CliSiTef

O CliSiTef (lib TEF da Software Express) não é request/response — é um loop interativo que emite comandos para a UI a cada iteração e espera resposta. Modelar isso como IDuplexCall<TUp, TDown> elimina classes inteiras de bug.

Por que não request/response com um transactionId

A tentação é fazer a UI iniciar uma transação, receber um txId, e depois mandar/receber mensagens por chamadas separadas correlacionadas pelo id. Funciona — mas tem problemas:

  • Estado órfão: se a UI fechar abruptamente, o agente fica num loop esperando uma resposta que nunca vem; é preciso timeout + reaper.
  • Cancelamento espalhado: precisa de uma chamada extra Cancel(txId) e do agente tratar isso defensivamente.
  • Concorrência: dois callers podem invocar SubmitResponse(txId) ao mesmo tempo — a ordem das respostas vira problema seu.
  • Reconexão: ao reconectar, é preciso re-vincular o caller à sessão pelo txId.

Com duplex, a sessão é o par de canais. Cancelar o CancellationToken fecha os canais; o loop do agente para na próxima leitura; o stream do SignalR fecha; a UI sai do await foreach. Tudo atômico.

O contrato

[RpcContract]
public interface ITefService
{
    [RpcMethod(Id = 1)]
    IDuplexCall<TefResponse, TefEvent> Charge(TefRequest initial, CancellationToken ct);
}

public sealed record TefRequest(decimal Amount, string OperatorId, string MerchantReference);
public sealed record TefResponse(string Text);

[JsonPolymorphic(TypeDiscriminatorPropertyName = "$type")]
[JsonDerivedType(typeof(TefDisplayMessage), nameof(TefDisplayMessage))]
[JsonDerivedType(typeof(TefCollectInput),  nameof(TefCollectInput))]
[JsonDerivedType(typeof(TefMenu),          nameof(TefMenu))]
[JsonDerivedType(typeof(TefConfirm),       nameof(TefConfirm))]
[JsonDerivedType(typeof(TefCompleted),     nameof(TefCompleted))]
[JsonDerivedType(typeof(TefError),         nameof(TefError))]
public abstract record TefEvent;

public sealed record TefDisplayMessage(string Text) : TefEvent;
public sealed record TefCollectInput(string Prompt, int MinLength, int MaxLength) : TefEvent;
public sealed record TefMenu(string Title, IReadOnlyList<string> Options) : TefEvent;
public sealed record TefConfirm(string Prompt) : TefEvent;
public sealed record TefCompleted(string Nsu, string AuthorizationCode, string Receipt) : TefEvent;
public sealed record TefError(int Code, string Message) : TefEvent;
JsonPolymorphic é importante: sem o discriminator $type, o System.Text.Json não consegue deserializar o evento certo no caller. O JsonDuplexAdapter reaproveita o RpcJson.Options que já trata polimorfismo declarado dessa forma.

No lado do caller (Blazor)

await using var call = Rpc.For<ITefService>(
        RpcAddress.User(currentUserId, Capability.Tef))
    .Charge(new TefRequest(Amount, OperatorId, Reference), ct);

await foreach (var ev in call.Responses.WithCancellation(ct))
{
    switch (ev)
    {
        case TefDisplayMessage m:
            CurrentMessage = m.Text;
            StateHasChanged();
            break;

        case TefCollectInput ask:
            var answer = await PromptUserAsync(ask);
            await call.SendAsync(new TefResponse(answer), ct);
            break;

        case TefMenu menu:
            var pick = await ShowMenuAsync(menu.Options);
            await call.SendAsync(new TefResponse(pick), ct);
            break;

        case TefConfirm c:
            var ok = await ConfirmAsync(c.Prompt);
            await call.SendAsync(new TefResponse(ok ? "S" : "N"), ct);
            break;

        case TefCompleted ok:
            ShowReceipt(ok);
            return ok;

        case TefError err:
            throw new TefException(err.Code, err.Message);
    }
}

O await using garante DisposeAsync mesmo em exceção ou cancelamento — fechando o duplex e enviando DuplexCancel pro agente.

No lado do agente (impl que envolve o CliSiTef)

public IDuplexCall<TefResponse, TefEvent> Charge(TefRequest req, CancellationToken ct)
{
    var call = new DuplexCallChannel<TefResponse, TefEvent>(ct);
    _ = Task.Run(() => RunCliSiTefLoopAsync(req, call), call.Token);
    return call;
}

private async Task RunCliSiTefLoopAsync(TefRequest req, DuplexCallChannel<TefResponse, TefEvent> call)
{
    var ct = call.Token;
    try
    {
        int rc = CliSiTef.IniciaFuncaoSiTefInterativo(funcao: 0, valor: req.Amount, /* ... */);

        while (rc == 10000) // 10000 = "continua o loop"
        {
            var prompt = CliSiTef.LeUltimoComando();
            var ev = TefEventMapper.From(prompt);   // traduz comando CliSiTef → TefEvent
            await call.Emit.WriteAsync(ev, ct);

            if (ev.RequiresResponse)
            {
                var resp = await call.Received.ReadAsync(ct);
                rc = CliSiTef.ContinuaFuncaoSiTefInterativo(resp.Buffer, /* ... */);
            }
            else
            {
                rc = CliSiTef.ContinuaFuncaoSiTefInterativo(null, /* ... */);
            }
        }

        if (rc == 0)
            await call.Emit.WriteAsync(new TefCompleted(/* NSU, auth, receipt */), ct);
        else
            await call.Emit.WriteAsync(new TefError(rc, CliSiTef.LeUltimaMensagem()), ct);
    }
    catch (OperationCanceledException)
    {
        // operador cancelou ou caller disposou → derrubar a transação no SiTef
        CliSiTef.FinalizaTransacaoSiTef(confirma: 0, /* desfaz */);
    }
    finally
    {
        call.Emit.Complete();
    }
}

O DuplexCallChannel<TUp, TDown> expõe duas APIs ao mesmo objeto: uma caller-side (que vai pro proxy: SendAsync, Responses) e uma impl-side (que a implementação usa internamente: Emit, Received). É a mesma classe, com pontas opostas.

Confirmação pós-impressão (gotcha do CliSiTef)

O SiTef exige uma confirmação explícita depois que o cupom é impresso — sem ela, a transação fica em estado pendente no adquirente. No modelo duplex isso é só mais uma rodada de evento+resposta no mesmo canal: 

await call.Emit.WriteAsync(
    new TefConfirm("Imprimir via do cliente? Confirme após impressão (S/N)"), ct);

var confirm = await call.Received.ReadAsync(ct);
if (!confirm.Text.Equals("S", StringComparison.OrdinalIgnoreCase))
{
    // desfaz no SiTef
    CliSiTef.FinalizaTransacaoSiTef(confirma: 0, /* ... */);
    await call.Emit.WriteAsync(
        new TefError(-1, "Cliente recusou confirmação. Transação desfeita."), ct);
    return;
}
// confirma
CliSiTef.FinalizaTransacaoSiTef(confirma: 1, /* ... */);

Modos de falha — todos cobertos

SituaçãoO que acontece
Operador clica "Cancelar" no Blazor CancellationToken cancela → call.DisposeAsync() → DuplexCancel(corr) chega no agente → cts.Cancel() no RunCliSiTefLoopAsync → o await em call.Received.ReadAsync(ct) joga OperationCanceledException → FinalizaTransacaoSiTef(confirma: 0) no finally.
Caller fecha o navegador (Blazor circuit perdido) SignalR cliente desconecta → OnDisconnectedAsync no Hub → pendingDuplexes.CancelAllForConnection(...) → mesma cadeia de cancelamento do caso anterior.
Agente trava ou cai durante o loop OnDisconnectedAsync do agente → o downstream channel é completado com RpcException → o caller pega num catch.
Resposta do CliSiTef é não-zero (erro de adquirente, cartão recusado) Impl emite TefError com o código e a mensagem.
Cliente recusa confirmação pós-impressão Vira mais um TefConfirm → TefResponse("N") → impl chama FinalizaTransacaoSiTef(0) e emite TefError.

Outros casos que viram duplex

O padrão se aplica a qualquer interação multi-rodada:

  • Cancelamento TEF — outro método na mesma ITefService, mesma forma de duplex.
  • Pré-autorização e captura — também duplex.
  • Consulta de saldo — pode ser request/response simples se não pede input do operador.
  • Coleta de assinatura digital — duplex (Display "assine" → CollectInput de bitmap → Completed).
  • Operações longas com progresso (impressão de relatório grande) — pode ser stream simples (IAsyncEnumerable<PrintProgress>) sem precisar de TUp; o RpcKit suporta isso via OpenStreamAsync.
