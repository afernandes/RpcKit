Conceitos

Endereçamento

O endereço diz quem deve responder a uma chamada. RpcKit oferece quatro variantes cobrindo os modos de roteamento típicos de sistemas multi-dispositivo.

As quatro variantes de RpcAddress

VarianteConstrutorQuando usar
SERVER RpcAddress.Server Handler local no servidor. Sem hop pela rede em modo in-process (InProcessRpcInvoker).
DEVICE RpcAddress.Device(deviceId) Direto a um device específico já conectado (ex: PDV-02 pinga o PDV-01).
ROLE RpcAddress.Role(capability, tenantId) Primeiro device do tenant que declarou a capability (ex: qualquer impressora da cozinha).
USER RpcAddress.User(userId, capability) O device do usuário logado que tem a capability (ex: o pinpad TEF do operador X).

Server

O alvo é um handler registrado no servidor via DispatcherRegistry.RegisterInvoke(...).

var orders = await Rpc.For<IOrderService>(RpcAddress.Server)
                      .GetOpenOrdersAsync(ct);

No Sample.Server.Api, o DispatcherStartup registra o handler de IOrderService na inicialização.

Device

O caller sabe o DeviceId exato do alvo. O DeviceRegistry resolve para o ConnectionId ativo daquele device.

var pong = await Rpc.For<IPosTerminal>(RpcAddress.Device("PDV-02"))
                    .PingAsync(ct);
Atenção: se o device estiver offline, a chamada lança RpcException com Kind = "RouteNotFound". Isso é coberto pelo teste Invoke_to_offline_device_throws_RouteNotFound.

Role

O caller sabe a capability que precisa, e o tenant. O router pega o primeiro device disponível com aquela capability dentro do tenant.

await Rpc.For<IPrinterService>(
        RpcAddress.Role(Capability.PrinterKitchen, tenantId))
    .PrintAsync(new PrintJob("Pedido 1", "1x Pizza"), ct);

Capabilities pré-definidas (em Capability): Tef, PrinterKitchen, PrinterPdv, PosTerminal. Defina as suas próprias com new Capability("seu.nome").

User

O caso TEF. O caller (Blazor) sabe quem é o operador logado; o router precisa achar o device daquele operador com a capability TEF. Roteamento de granularidade fina.

var tef = Rpc.For<ITefService>(
    RpcAddress.User(currentUserId, Capability.Tef));
Multi-tenant no futuro: os quatro construtores já carregam (ou serão capazes de carregar) tenantId. Quando o sistema virar SaaS multi-tenant, basta o DeviceRegistry particionar por tenant e o Hub validar tenant_id nos claims do JWT. Os contratos e as chamadas não mudam.

Handshake do agente — IRpcIdentityProvider

O agente declara seu endereçamento ao conectar — via query string da URL do Hub. A identidade (DeviceId + UserId + TenantId + Capabilities) é fornecida por uma implementação de IRpcIdentityProvider registrada no DI. Uma única interface, um único método, leitura atômica.

Caso 1 — Identidade fixa (worker service, kiosk, dev)

Pro caso comum onde a identidade do agente não muda durante o processo (service account, kiosk com login feito antes), use o atalho UseStaticIdentity: 

services.AddRpcClient(o =>
{
    o.HubUrl = "https://api.foo.com/rpc";
    o.AccessTokenProvider = () => GetJwtAsync();   // JWT continua sendo Func — vai direto pro SignalR
})
.UseStaticIdentity(new RpcIdentity(
    DeviceId: "PDV-01",
    UserId: "operator-1",
    TenantId: "tenant-x",
    Capabilities: [Capability.Tef, Capability.PrinterPdv]));

Resulta numa URL como:

https://api.foo.com/rpc?deviceId=PDV-01&tenantId=tenant-x&userId=operator-1&caps=tef,printer.pdv

O RpcHub.OnConnectedAsync parseia esses valores e registra a entrada no DeviceRegistry.

Em produção: os valores acima devem vir dos claims do JWT, não da query string. O fluxo de handshake fica o mesmo, mas o servidor lê Context.User em vez de Context.GetHttpContext().Request.Query. Este é um TODO simples quando você integrar autenticação ASP.NET.

Caso 2 — Identidade dinâmica (login após startup)

Em apps com tela de login, o UserId só é conhecido depois do operador logar e pode trocar durante a sessão. Implemente IRpcIdentityProvider com sua lógica e registre via UseIdentityProvider<T>: 

public sealed class AppIdentityProvider(
    ISessionStore session,
    IMachineFingerprint fingerprint,
    IHardwareScan hardware) : IRpcIdentityProvider
{
    public async Task<RpcIdentity> GetIdentityAsync(CancellationToken ct)
    {
        var current = await session.GetCurrentAsync(ct);
        var caps = new List<Capability>();
        if (await hardware.HasPinpadAsync(ct))  caps.Add(Capability.Tef);
        if (await hardware.HasPrinterAsync(ct)) caps.Add(Capability.PrinterPdv);

        return new RpcIdentity(
            DeviceId: await fingerprint.GetAsync(ct),
            UserId: current?.UserId,
            TenantId: current?.TenantId,
            Capabilities: caps);
    }
}

// no DI setup:
services.AddSingleton<ISessionStore, SessionStore>();
services.AddSingleton<IMachineFingerprint, MachineFingerprint>();
services.AddSingleton<IHardwareScan, HardwareScan>();

services.AddRpcClient(o =>
{
    o.HubUrl = "https://api.foo.com/rpc";
    o.AccessTokenProvider = sp => sp.GetRequiredService<ISessionStore>().GetJwtAsync();
})
.UseIdentityProvider<AppIdentityProvider>();

Vantagens da interface sobre callbacks separados: leitura atômica da sessão (só um round-trip), injeção de dependências natural no construtor, testabilidade simples via mock da interface, e contrato claro (1 método, 1 retorno).

Reconectar após login/logout

O IRpcIdentityProvider.GetIdentityAsync é chamado UMA vez por ciclo de conexão. Pra trocar identidade quando o usuário loga/desloga, dispare ReconnectAsync() — ele descarta a conexão atual e abre uma nova, re-invocando o provider: 

public sealed class LoginPage(RpcConnectionHost rpc, ISessionStore session)
{
    public async Task OnLoginAsync(string username, string password)
    {
        var result = await Authenticate(username, password);
        await session.SetCurrentAsync(result);
        await rpc.ReconnectAsync();   // ← agora o agente reconecta como o usuário X
    }

    public async Task OnLogoutAsync()
    {
        await session.ClearAsync();
        await rpc.ReconnectAsync();   // ← reconecta sem UserId (modo device-only)
    }
}
Por que não Func<Task<string?>> separados pra cada campo? Identidade é estado coeso — você lê tudo da mesma sessão, no mesmo instante. 4 callbacks forçariam 4 round-trips ao session store. Uma interface com um método garante atomicidade.
O AccessTokenProvider permanece como Func<Task<string?>> porque é repassado diretamente ao SignalR sem nossa intermediação — manter consistência com a API dele.

Blazor Server não usa AddRpcClient

Vale repetir: o Blazor Server hospeda o Hub via AddRpcServer(). Ele não conecta a si mesmo. O usuário corrente nas chamadas vem do AuthenticationStateProvider da request — não do handshake. 

// no Demo.Web/Program.cs:
builder.Services.AddScoped<ICurrentTefUser>(sp =>
{
    var auth = sp.GetRequiredService<AuthenticationStateProvider>();
    var state = auth.GetAuthenticationStateAsync().Result;
    var userId = state.User.FindFirst("sub")?.Value ?? "anonymous";
    return new DemoTefUser(userId);
});

builder.Services.AddScoped<ITefAddressResolver, CurrentUserTefAddressResolver>();
// CurrentUserTefAddressResolver.Resolve = RpcAddress.User(currentUser.UserId, Capability.Tef)

Cada request HTTP cria seu próprio escopo. O ICurrentTefUser resolve o usuário do request corrente, e o ITefAddressResolver monta o RpcAddress.User(...) certo na hora da chamada. Zero envolvimento de startup.

O que o router resolve em cada caso

EndereçoO router faz
ServerAddressAcha o dispatcher local em DispatcherRegistry e roda.
DeviceAddressDeviceRegistry.ResolveByDeviceId(...)
RoleAddressDeviceRegistry.ResolveByCapability(cap, tenantId) — primeiro match.
UserAddressDeviceRegistry.ResolveByUserCapability(userId, cap)
