Conceitos

Source Generator

Rpc.SourceGen é um Roslyn generator que detecta interfaces marcadas com [RpcContract] e emite proxy + dispatcher em tempo de compilação. Você só escreve a interface; o resto vira código gerado.

Sem o gerador: ~30 linhas hand-written por contrato (proxy + dispatcher + serialização) que precisam ficar sincronizadas com a interface.
Com o gerador: 0 linhas. A interface é a única fonte de verdade.

Quando usar (e quando NÃO usar)

Use quandoNÃO use quando
Você está definindo um novo contrato [RpcContract]. O método precisa de out ou ref params.
Os retornos cabem em Task<T>, Task, IAsyncEnumerable<T> ou IDuplexCall<TUp, TDown>. O método é genérico (Task<T> Foo<T>()) — generic methods não são suportados.
Os parâmetros são tipos JSON-serializáveis. Você precisa de wire-format customizado (MessagePack, Protobuf) — esse generator só emite código que usa System.Text.Json.

Instalação

Via NuGet (consumidor da biblioteca)

dotnet add package RpcKit.SourceGen

Importante: o package também precisa que você tenha RpcKit.Contracts (para as anotações [RpcContract]) e RpcKit.Core (para os tipos referenciados no código gerado: IRpcInvoker, RpcAddress, DeferredDuplexCall, etc). Esses são puxados automaticamente se você instalou RpcKit.SignalR.Client ou RpcKit.SignalR.Server.

Via ProjectReference (dev local nos kits)

<ItemGroup>
  <ProjectReference Include="..\..\src\Rpc.SourceGen\Rpc.SourceGen.csproj"
                    OutputItemType="Analyzer"
                    ReferenceOutputAssembly="false" />
</ItemGroup>

Os dois atributos são obrigatórios: OutputItemType="Analyzer" faz o MSBuild passar a DLL pro compilador C# como analyzer (não como referência runtime); ReferenceOutputAssembly="false" evita que a DLL do generator seja copiada pra bin/.

Passo a passo: do zero ao RPC funcionando

Passo 1 — Defina a interface

using Rpc.Contracts;

namespace MyApp.Contracts;

[RpcContract]
public interface IInventoryService
{
    [RpcMethod(1)]
    Task<StockLevel> GetStockAsync(string sku, CancellationToken ct);

    [RpcMethod(2, Exclusive = true)]
    Task<bool> ReserveAsync(string sku, int qty, string customerId, CancellationToken ct);

    [RpcMethod(3)]
    IAsyncEnumerable<StockMovement> StreamMovementsAsync(string sku, CancellationToken ct);

    [RpcMethod(4)]
    IDuplexCall<StockCommand, StockEvent> SubscribeAsync(SubscribeRequest req, CancellationToken ct);
}

public sealed record StockLevel(string Sku, int Quantity, DateTimeOffset MeasuredAt);
public sealed record StockMovement(DateTimeOffset At, int Delta, string Reason);
public sealed record SubscribeRequest(string[] Skus);
public abstract record StockCommand;
public abstract record StockEvent;

Passo 2 — Compile

É só rodar dotnet build. O gerador roda durante a compilação e produz um arquivo por interface: 

YourProject/obj/Debug/net10.0/generated/Rpc.SourceGen/Rpc.SourceGen.RpcContractGenerator/
└── IInventoryService.RpcGenerated.g.cs

Esse arquivo contém:

  • MyApp.Contracts.Generated.InventoryServiceProxy — implementa IInventoryService, serializa args, chama IRpcInvoker.
  • MyApp.Contracts.Generated.InventoryServiceDispatcher — método estático Register(IDispatcherRegistry, IInventoryService).
  • Records auxiliares __IInventoryService_{Method}_Args pra métodos com 2+ parâmetros.

Passo 3 — Registre o proxy no caller (3 opções)

O gerador emite extension methods que escondem o boilerplate.

Opção A — Registra TUDO de uma vez (recomendado quando todos os contratos do assembly são usados):

using MyApp.Contracts.Generated;

// no DI setup do caller — uma linha registra todos os proxies do assembly:
proxies.AddAllMyAppContractsProxies();
//      └──────────────────────────┘
//      "MyAppContracts" vem do AssemblyName, garante unicidade quando
//      múltiplos kits são consumidos juntos (TefKit + PrintKit + ...).

Opção B — Por contrato (quando você quer escolher quais registrar):

proxies.AddInventoryServiceProxy()
       .AddOrderServiceProxy()
       .AddPosTerminalProxy();
//      └────────────────┘
//      gerado por contrato — sintaxe fluente.

Opção C — Manual (legado), ainda funciona:

proxies.Register(typeof(IInventoryService),
    static (inv, addr) => new InventoryServiceProxy(inv, addr));

Passo 4 — Registre o dispatcher no agente/servidor (3 opções)

O lado que TEM a implementação registra o dispatcher gerado.

Opção A — Explícita, com o impl em mãos:

using MyApp.Contracts.Generated;

var impl = new InventoryServiceImpl(db);
dispatchers.AddInventoryServiceDispatcher(impl);

Opção B — DI resolve o impl (concisa quando o impl já está no container):

dispatchers.AddInventoryServiceDispatcher(serviceProvider);
//                                       └─────────────┘
//                                       resolve via sp.GetService(typeof(IInventoryService))
//                                       — lança InvalidOperationException se não registrada.

Opção C — Estática (gerada também, equivalente à opção A):

InventoryServiceDispatcher.Register(dispatchers, impl);
Por que o nome do método inclui o assembly? Para evitar colisão. TefKit.Contracts emite AddAllTefKitContractsProxies; PrintKit.Contracts emite AddAllPrintKitContractsProxies. Se ambos registrassem AddAllGeneratedProxies, o C# rejeitaria a chamada como ambígua quando os dois using estivessem em escopo. Os métodos POR CONTRATO (AddInventoryServiceProxy) já são únicos por natureza.

Passo 5 — Use

// no caller:
var inv = Rpc.For<IInventoryService>(RpcAddress.Server);
var stock = await inv.GetStockAsync("SKU-001", ct);

// duplex:
await using var sub = inv.SubscribeAsync(new SubscribeRequest(["SKU-1", "SKU-2"]), ct);
await sub.SendAsync(new StartCommand(...));
await foreach (var evt in sub.Responses.WithCancellation(ct))
    Process(evt);

// stream:
await foreach (var mov in inv.StreamMovementsAsync("SKU-001", ct).WithCancellation(ct))
    Display(mov);

Tipos de retorno suportados

Retorno na interface Gera proxy chamando Gera dispatcher registrando
Task<T> / ValueTask<T> IRpcInvoker.InvokeAsync + JsonSerializer.Deserialize<T> RegisterInvoke — chama impl + serializa T
Task / ValueTask IRpcInvoker.InvokeAsync ignorando o resultado RegisterInvoke — chama impl + retorna null
IAsyncEnumerable<T> OpenStreamAsync + async iterator deserializando cada chunk RegisterStream — método privado async iterator serializando cada item
IDuplexCall<TUp, TDown> OpenDuplexAsync + retorna DeferredDuplexCall<TUp, TDown> RegisterDuplex com pumps bidirecionais (upstream → impl + impl.Responses → downstream)
NÃO suportado (silenciosamente ignorado): métodos sem [RpcMethod], métodos com retorno void, int, string ou qualquer tipo não-Task/IAsyncEnumerable/IDuplexCall. Use Task mesmo pra "fire and forget" — RPC é assíncrono por natureza.

Como o gerador trata cada parâmetro

CasoComo serializaCódigo gerado (resumido)
Sem parâmetros (só CancellationToken) Payload fixo "{}" var __payload = "{}";
1 parâmetro + opcionalmente CT Serializa o tipo diretamente var __payload = JsonSerializer.Serialize(arg, RpcJson.Options);
2+ parâmetros (+ opcionalmente CT) Empacota num record internal gerado var __payload = JsonSerializer.Serialize(new __IFoo_Bar_Args(a, b, c), RpcJson.Options);
CancellationToken em qualquer posição Detectado automaticamente; não vai no payload; passado pro invoker e pro impl cancellationToken: ct

Flag Exclusive

[RpcMethod(N, Exclusive = true)] faz o router rejeitar uma 2ª chamada concorrente pra mesmo agente com RpcBusyException, antes mesmo de chegar no agente. 

[RpcContract]
public interface ITefService
{
    [RpcMethod(1, Exclusive = true)]   // ← pinpad só processa uma transação por vez
    IDuplexCall<TefResponse, TefEvent> Charge(TefRequest req, CancellationToken ct);
}

Use em recursos one-at-a-time: pinpad TEF, gaveta de dinheiro, leitor biométrico. Não use em recursos que aceitam fila (impressora). Mais detalhes em Concorrência.

Como inspecionar o código gerado

Por padrão os arquivos .g.cs vivem em memória — o compilador os usa mas não persiste em disco. Pra debugá-los, adicione ao csproj que consome o gerador: 

<PropertyGroup>
  <EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>
  <CompilerGeneratedFilesOutputPath>$(BaseIntermediateOutputPath)GeneratedFiles</CompilerGeneratedFilesOutputPath>
</PropertyGroup>

Depois do próximo dotnet build os arquivos aparecem em:

obj/GeneratedFiles/Rpc.SourceGen/Rpc.SourceGen.RpcContractGenerator/
├── IInventoryService.RpcGenerated.g.cs
├── ITefService.RpcGenerated.g.cs
└── ...

Útil pra entender exatamente o que o gerador produziu, comparar entre versões, ou debugar por que algum tipo gerado não está sendo encontrado.

Anatomia da saída — exemplo real

Para ITefService.Charge (duplex com 1 arg + CT, Exclusive=true), o gerador emite aproximadamente: 

// <auto-generated by Rpc.SourceGen v1.0.0 />
namespace Sample.Contracts.Generated;

public sealed class TefServiceProxy : global::Sample.Contracts.ITefService
{
    public const string ContractId = "ITefService";

    private readonly global::Rpc.Core.IRpcInvoker __invoker;
    private readonly global::Rpc.Core.RpcAddress __address;

    public TefServiceProxy(global::Rpc.Core.IRpcInvoker invoker, global::Rpc.Core.RpcAddress address)
    {
        this.__invoker = invoker;
        this.__address = address;
    }

    public global::Rpc.Contracts.IDuplexCall<TefResponse, TefEvent> Charge(
        TefRequest initial,
        global::System.Threading.CancellationToken cancellationToken = default)
    {
        var __payload = global::System.Text.Json.JsonSerializer.Serialize(initial, global::Rpc.Core.RpcJson.Options);
        var __openTask = __invoker.OpenDuplexAsync(__address, ContractId, 1, __payload,
            exclusive: true,                        // ← veio do [RpcMethod(1, Exclusive = true)]
            cancellationToken: cancellationToken);
        return new global::Rpc.Core.DeferredDuplexCall<TefResponse, TefEvent>(__openTask);
    }
}

public static class TefServiceDispatcher
{
    public const string ContractId = "ITefService";

    public static void Register(global::Rpc.Core.IDispatcherRegistry registry, global::Sample.Contracts.ITefService implementation)
    {
        registry.RegisterDuplex(ContractId, 1, async (__initialJson, __upstream, __downstream, __ct) =>
        {
            var __arg0 = global::System.Text.Json.JsonSerializer.Deserialize<TefRequest>(__initialJson, global::Rpc.Core.RpcJson.Options)!;
            await using var __typedCall = implementation.Charge(__arg0, __ct);

            // pump upstream → impl
            var __pumpUp = global::System.Threading.Tasks.Task.Run(async () =>
            {
                try
                {
                    await foreach (var __json in __upstream.ReadAllAsync(__ct))
                    {
                        var __resp = global::System.Text.Json.JsonSerializer.Deserialize<TefResponse>(__json, global::Rpc.Core.RpcJson.Options);
                        if (__resp is not null) await __typedCall.SendAsync(__resp, __ct);
                    }
                }
                catch (global::System.OperationCanceledException) { }
                finally { await __typedCall.CompleteAsync(); }
            }, __ct);

            // pump impl.Responses → downstream
            try
            {
                await foreach (var __ev in __typedCall.Responses.WithCancellation(__ct))
                {
                    var __json = global::System.Text.Json.JsonSerializer.Serialize<TefEvent>(__ev, global::Rpc.Core.RpcJson.Options);
                    await __downstream.WriteAsync(__json, __ct);
                }
            }
            finally
            {
                try { await __pumpUp; } catch { }
            }
        });
    }
}

Note que o código gerado:

  • Usa global:: em todos os tipos — não depende de using do consumer.
  • Marca [GeneratedCode] — invisível para code coverage / análise.
  • Reaproveita RpcJson.Options — serializer compartilhado, polymorphism resolvido.

Versionamento dos contratos

O MethodId em [RpcMethod(N)] é a chave de wire. O nome em C# é só pra programador. Regras de evolução:

MudançaCompatível?Como fazer
Renomear método em C# ✅ Mantenha o mesmo ID. Clientes antigos seguem chamando pelo wire-id.
Adicionar novo método ✅ Use o próximo ID livre.
Adicionar campo opcional ao DTO ✅ System.Text.Json ignora membros faltantes por padrão.
Alterar tipo de parâmetro ou retorno ❌ quebra wire Crie [RpcMethod(N+1)] novo com o tipo novo. Marque o antigo [Obsolete].
Remover método ❌ pra clientes antigos Queime o ID — nunca reutilize. Mantenha o método [Obsolete] por uma versão.
Renomear DTO em C# ✅ JSON serializa por nome de propriedade, não de tipo.
Renomear propriedade do DTO ❌ Wire é JSON com nome de campo — quebra. Use [JsonPropertyName] pra manter wire estável.

Erros comuns e debugging

"O nome 'FooProxy' não existe no contexto atual"

Causa típica: você esqueceu de adicionar using YourNs.Generated;. O gerador coloca os tipos no sub-namespace .Generated, não na mesma namespace do contrato.

Nada é gerado mesmo com [RpcContract] na interface

Verifique:

  • O projeto referencia o gerador como OutputItemType="Analyzer"?
  • Pelo menos um método tem [RpcMethod(N)]? Interfaces sem nenhum método marcado são ignoradas.
  • O atributo é Rpc.Contracts.RpcContractAttribute e não outro com mesmo nome curto?

Pra inspeção rápida: ative EmitCompilerGeneratedFiles e veja se o arquivo .g.cs aparece. Se não aparecer, o gerador não enxergou a interface.

Um método específico não foi gerado

O gerador silenciosamente pula métodos com:

  • Retorno fora dos 4 padrões suportados (ex: void, int, IObservable<T>).
  • Sem o atributo [RpcMethod(N)].
  • Genéricos no método (Task<T> Foo<T>()).

"Id é não um argumento de atributo nomeado válido"

[RpcMethod(Id = 1)] não compila porque Id é parâmetro do construtor. Use positional: [RpcMethod(1)] ou [RpcMethod(1, Exclusive = true)].

Dois contratos com mesmo nome curto colidem no ContractId

O ContractId é o nome curto da interface ("IOrderService"). Se você tem MyApp.Sales.IOrderService e MyApp.Kitchen.IOrderService no mesmo Hub, vão colidir. Rename um deles ou use namespace prefix manual no contractId (não suportado nativamente — vira fork do gerador).

Limitações conhecidas

  • Sem suporte a out/ref params — incompatível com RPC.
  • Sem generic methods — Task<T> Foo<T>() não funciona. Use generic interfaces ou método não-genérico com discriminador.
  • Sem default interface methods — só métodos declarados são gerados.
  • JSON serializer é fixo em RpcJson.Options. Pra trocar, você precisaria forkar o gerador. Plano: tornar configurável via attribute futuramente.
  • Args record para 2+ params gera um record internal extra. Adiciona ~1KB ao IL gerado por método.
  • Tipos referenciados precisam estar acessíveis — não pode haver tipo internal do parâmetro num assembly e a interface em outro.

Como o gerador funciona por dentro

IIncrementalGenerator (Roslyn API moderna, mais rápida que ISourceGenerator). Pipeline:

  1. ForAttributeWithMetadataName("Rpc.Contracts.RpcContractAttribute") filtra apenas InterfaceDeclarationSyntax com o atributo — barato e cached.
  2. ContractModel.Build(ctx, ct) usa o SemanticModel pra extrair: nome da interface, namespace, métodos com [RpcMethod], classificação do retorno (INamedTypeSymbol.ConstructedFrom comparado com Task<T>, IAsyncEnumerable<T>, IDuplexCall<TUp, TDown>), parâmetros com seus tipos qualificados.
  3. ContractEmitter.Emit(model) constrói o C# como string com StringBuilder — sem AST manipulation, sem syntax tree rewriting. Mais simples e mais previsível.
  4. RegisterSourceOutput adiciona o resultado como arquivo gerado com hint name {InterfaceShortName}.RpcGenerated.g.cs.

FAQ

Posso ter contratos num assembly e implementações em outro?

Sim — esse é o pattern normal. O gerador roda no assembly que contém a interface marcada. Os tipos gerados ficam nesse assembly. O assembly que implementa a interface não precisa ter o gerador, só uma referência ao assembly de contratos.

O gerador funciona em CI / build server?

Sim. Roslyn analyzers funcionam em qualquer ambiente .NET SDK ≥ 7. O setup-dotnet@v4 do GitHub Actions já vem com tudo necessário. O CI dos 4 repos do RpcKit/TefKit/PrintKit roda exatamente assim.

Posso compartilhar contratos entre client e server?

Esse é o objetivo. Um único assembly de contratos é referenciado pelo client (que pega o proxy gerado) e pelo server/agente (que pega o dispatcher gerado). Ambos têm o gerador rodando — emite os dois tipos no mesmo arquivo.

Posso desabilitar pra um projeto específico?

Sim. Remova a ProjectReference com OutputItemType="Analyzer" ou o package RpcKit.SourceGen. As classes geradas somem do build seguinte.

O gerador altera meu código-fonte?

Nunca. Roslyn generators são aditivos — só emitem novos arquivos. Seu código existente nunca é tocado.

Quanto custa em tempo de build?

Negligível. Em projetos com 4 contratos, <50ms a mais de build. Incremental — só reroda quando o syntax tree dos arquivos com [RpcContract] muda.

Posso ver o que ele gerou antes de compilar?

Não — o gerador roda durante a compilação. Mas pode ver depois ativando EmitCompilerGeneratedFiles (seção acima). Outra opção: use o Roslyn Syntax Visualizer no Visual Studio pra inspecionar o syntax tree gerado.
